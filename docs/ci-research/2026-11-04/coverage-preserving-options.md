# Coverage-preserving CI acceleration options

Research date: 4 November 2026. Planning only; no benchmark, workflow dispatch, native build, cache deletion or settings change was performed.

Question: [Which CI acceleration options preserve coverage on free runners?](https://github.com/pennel-app/pennel/issues/151), within [Make Pennel PR checks faster without losing coverage](https://github.com/pennel-app/pennel/issues/149). Existing implementation and acceptance remain with [Accelerate CI while preserving affected-platform coverage](https://github.com/pennel-app/pennel/issues/73).

The feasible mechanisms are removing repeated work inside existing jobs, isolating independent work before overlapping it, and transferring narrowly defined inputs with verified provenance. None establishes a latency improvement without a matched measurement. No final architecture or numeric latency target is selected here.

## Free-runner and storage boundaries

The repository API reported public visibility and the organization API reported plan `free`. Current official documentation says standard hosted runner use is free for public repositories; its ARM64 Mac specification is 3 M1 CPUs/7 GB RAM/14 GB SSD. GitHub Free documents 20 concurrent jobs with at most five macOS jobs. These limits are capacity ceilings, not queue guarantees. A core-touch cohort already selects four Mac jobs across core, desktop, mobile and evaluation; replacing one mobile job with three can create six Mac jobs before another PR or release competes. [Hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [Actions limits](https://docs.github.com/en/actions/reference/limits).

Contemporaneous timing research also shows why scheduling belongs in the decision. A [sample desktop run](https://github.com/pennel-app/pennel/actions/runs/41726226537) took 77m17s overall: its Mac app executed for 9m32s but started 67m44s after the workflow event. The version dependency ended at 1m22s, leaving a 66m22s dependency-satisfied scheduling interval; the actual ready boundary and precise cause are unknown. A [sample mobile run](https://github.com/pennel-app/pennel/actions/runs/41725798670) took 95m01s overall, comprising 36m19s event-to-start and 58m41s execution (rounding accounts for the second). Adding concurrent Mac jobs can worsen contention; these samples do not diagnose a quota or runner-capacity root cause.

GitHub currently includes 10 GB cache storage per repository; usage beyond the free allowance is billed when opted in. Entries unused for seven days expire and exceeding configured capacity can evict older entries and cause churn. This is distinct from Pennel's existing, stricter experiment guard of **10,000,000,000 bytes including a 100,000,000-byte reserve**. At the observed usage that guard would reject a cold experiment even before adding a seed. There is no demonstrated free headroom for a new CAS archive. Do not increase limits or remove working caches to make a candidate fit. [GitHub cache policy](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#usage-limits-and-eviction-policy), [current guard][xcode-cache].

## Isolation and invalidation contracts

**Separate DerivedData alone is insufficient for concurrent mobile configurations.** The locked Expo autolinking script replaces its product XCFramework, repoints shared-dependency symlinks and records the last configuration. React Native's locked script removes/reextracts a shared dependencies location and writes its configuration marker. That is direct evidence of mutable inputs outside DerivedData. Isolate the complete checkout, node_modules, generated iOS/Pods, prepared frameworks and build outputs per concurrent native process; check for symlinks back into a mutable shared workspace. Independent hosted jobs provide separate VMs. Same-host copies need proof of equivalent isolation and sufficient disk/RAM; no such proof was produced here. [Locked Expo implementation](https://github.com/expo/expo/blob/expo-modules-autolinking@58.0.15/packages/expo-modules-autolinking/scripts/ios/replace-xcframework.js), [locked React Native implementation](https://github.com/react/react-native/blob/v0.88.0/packages/react-native/third-party-podspecs/replace_dependencies_version.js), [locked package versions][mobile-lock].

**Generation remains validation.** Expo documents that clean generation deletes native projects, while repeated non-clean generation layers modifications and can differ for non-idempotent plugins. Replacing these tests with a cached generated project would erase the thing being tested. Retain the clean/twice-non-clean/clean equivalence regression, then the actual locked pod graph/provider/linker/source-membership checks. [Expo CNG](https://docs.expo.dev/workflow/continuous-native-generation/#clean), [Prebuild regression][prebuild-test], [pod ownership tests][pods-test].

**Native input reuse needs a complete contract.** At minimum record producer commit and repository/run identity; all core/keyboard source and Cargo locks/configuration/build scripts; Rust/Cargo/Xcode and both SDK builds; host/target architecture, deployment target, profile, feature set, effective Rust/native compiler flags, variant and UniFFI version; and checksums for both engine/keyboard XCFramework slices, generated Swift/header/modulemap and referenced symbols. Add npm/pod locks, app config/plugins/modules, assets and generated properties if their outputs are reused. Exact-source artifacts and a complete manifest are the first qualification scope; broader compatible cross-commit reuse is a separate decision. The existing Cloud fingerprint/validator provides useful patterns but only for its explicitly device-only contract. [Dual-target preparation][mobile-core], [keyboard preparation][keyboard-core], [Cloud native validator][native-cache], [CAS fingerprint][xcode-cache].

Artifacts need explicit hard-failing checksum/provenance validation: GitHub's automatic digest mismatch currently produces a warning. Preserve symlink semantics intentionally in prepared bundles and reject unsafe extraction paths; do not copy unverified generated workspaces with absolute paths. Keep secrets/signing keychains/profiles and preview/production content out of reusable inputs. Preserve the present unsigned Release and ad hoc Debug test signing behavior. [Artifact transport/validation](https://docs.github.com/en/actions/tutorials/store-and-share-data#validating-artifacts), [mobile workflow][mobile], [Makefile][make].

Cache scope is not an artifact attestation. Base/default-branch caches can be read by PRs; PR-created caches are merge-ref scoped. Maintain trusted-main writers, compiler/configuration keys and untrusted-run isolation. Never promote a PR-produced native artifact into a privileged release merely because its checksums match its own manifest. [GitHub cache isolation/security](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache).

Preserve desktop's main concurrency group around **version planning, builds and publication together**. Serializing only the final upload would leave version-selection races. Current `cancel-in-progress: false` protects a running main release; GitHub's default single pending slot can replace an older pending run, so “serialized” does not promise every queued push publishes. No release-concurrency change is proposed. [Desktop workflow][desktop], [GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

## Qualification required before choosing a design

1. Freeze a candidate and control source; compare equivalent events/merge-ref semantics, image version, Xcode/SDK/Rust/Node/pod identities, feature flags, variant and cache state. Include a full core-touch cohort and relevant mobile-only/desktop-only scopes; retain mixed/unknown-input cases. Read actual enforcement separately from workflow names; this research changes none.
2. Measure push-to-last-applicable-check completion. Separate dependency waiting, ready-runner queue, job execution and artifact/cache transfer. Record unavailable boundaries as unknown. Do not sum overlapping job durations or call phase sums total job execution. Added Mac jobs must be assessed alongside the existing cohort, not in an empty isolated workflow.
3. Establish all-success coverage equivalence, destination/architecture/binding manifests and appropriate failure/cancellation behavior before interpreting timing. Include toolchain/dependency/source/feature mutations and missing/corrupt artifacts; a restore miss must rebuild or explicitly fail the experiment, never silently omit validation.
4. For scheduling/dedup candidates, collect repeated matched complete cohorts and report median, spread and failures with setup/transfer/storage included; numeric acceptance targets remain for Lander. The frontend candidate has a small correctness surface; mobile isolation has greater possible overlap and greater queue/setup risk. This is an evidence distinction, not a final selection.
5. For native CAS, retain Pennel's existing **at least three matched warm observations with >=20% lower median total mobile-job execution**, a **matched cold control with <=10% regression**, complete passing checks and demonstrated fit within the existing free storage/policy allowance. Do not substitute mixed-image results or one warm pair. Confirm raw, packed and stored bytes, restore/save times and independently restored immutable seeds. [Existing acceptance protocol][performance].

The earlier pilot established one matched-image warm/control pair (38.57% lower execution), not the required three or a matched cold comparison. Its steady-state calculation was 10,868,098,256 bytes against the repository's 10,000,000,000-byte guard, so storage failed too. Xcode Cloud's later archive repetitions reported native cache misses and no established compilation gain; those are a different lane and do not repair the GitHub pilot's evidence gaps. Apple's supported compilation-cache mechanism does not imply hosted-runner portability or an adoption result. [Existing acceleration evidence](https://github.com/pennel-app/pennel/issues/73), [Cloud follow-up](https://github.com/pennel-app/pennel/issues/73#issuecomment-6556130496), [Xcode 26 compilation caching](https://developer.apple.com/documentation/xcode-release-notes/xcode-26-release-notes), [Apple cache settings](https://developer.apple.com/documentation/xcode/build-settings-reference).

Open human decisions: numeric targets, acceptable complexity/resource contention, which bounded experiment to authorize, and the final design. The research identifies feasible options and exclusion boundaries; it does not implement or dispatch them.
