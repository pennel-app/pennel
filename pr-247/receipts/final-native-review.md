## [P2] Preserve policy-specific cancellation through the desktop settings writer

**Location:** `apps/desktop/src-tauri/src/commands.rs:305` (`apply_settings_locked`).

**Trigger:** An automatic personal summary is running after Stop. In Settings → After a meeting, the owner changes the independent Suggestions policy or its fallback language. The Suggestions controls remain usable without an adopted suggestion qualification, so this direction is reachable with the current empty qualification registry. The reverse direction also applies to an admitted qualified suggestion job when the owner changes the Summary policy.

**Evidence:** The actual Suggestions writer calls `api.saveSettings(settings)` (`apps/desktop/src/meeting-suggestion-settings.ts:33`), as do the Summary consent/settings writers. Every desktop settings save reaches the unconditional `crate::inference::mutation(&shared.engine)` at `commands.rs:305`. That helper calls `engine.begin_inference_mutation()` (`apps/desktop/src-tauri/src/inference.rs:118–120`), which advances the global inference generation and cancels **all** registered core request tokens (`core/src/inference_engine.rs:79–89`). Automatic summaries register their token at `core/src/meeting_summary.rs:922–929`; admitted suggestions register theirs at `core/src/meeting_insight_engine.rs:1159–1174` and additionally compare the global epoch in `unchanged`.

Core's new per-policy revocation counters correctly keep these choices independent when `update_settings` is called directly, but the shell has already cancelled the unrelated work before that core policy handling runs. This leaves the accepted policy contract unmet in the production desktop route. The accepted suggestions ADR explicitly identifies this scenario and requires both directions of independence (paragraph beginning “Today a change to summary_automation cancels every in-flight inference request”, and the policy test requirement).

**Impact:** Changing only Suggestions can discard the pending automatic Summary result even though Summary remains Automatic. Changing only Summary can cancel Suggestions while Suggestions remains Automatic. The consumed automatic attempt marker remains, so the affected run does not resume or retry automatically; the owner must run it manually. Existing notes/transcript remain saved. This is one cancellation-boundary defect, not separate findings for each control.

**Smallest fix:** Make the desktop settings writer acquire the broad inference mutation guard only for changes that actually require global inference/configuration invalidation. At minimum, policy-only writes and the suggestion-language preference must bypass that broad guard and rely on the core's existing policy-specific cancellation. Preserve the broad guard for genuine provider/credential/inference configuration changes and preserve cancellation when the owner revokes the policy that owns the current automatic job. Do not remove or weaken the core revocation counters, consumed markers or finalization barriers.

**Meaningful covering test:** Exercise the actual desktop `change_settings`/`apply_settings_locked` route with an in-flight automatic Summary held at a controlled provider boundary. Save only `suggestion_automation` (and separately `suggestion_language`), release the provider and assert that Summary's token/epoch remain valid and its original admitted candidate commits. With an existing qualified test fixture, perform the reverse policy-only save during an automatic Suggestion job and assert completion/commit. Retain assertions that revoking the job's own policy cancels it and a true inference-configuration change still cancels it. Calling only `engine.update_settings` would miss this shell integration bug, as the current core policy tests already demonstrate the correct lower-level behavior.

**Confidence:** high. The production writer, unconditional mutation, token registration and cancellation are explicit; no device/runtime assumption or new provider qualification is required for the Summary-side trigger.
