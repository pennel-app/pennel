# Pennel — working rules

Pennel ships one product from one Rust core, with a shared desktop app and a shared mobile app:

- `core/` — `pennel-core`: all product logic (providers, cleanup, history, meetings, search, templates, export, local models, CLI agents). New behaviour goes here first.
- `apps/desktop/` — shared Tauri application for macOS, Windows and Linux.
- `apps/mobile/` — Expo/React Native mobile application, iPhone first and Android after iPhone acceptance. Native projects are generated by Prebuild; custom source and config plugins live outside those generated directories.
- `apps/mobile/native/ios/` — reusable iPhone services, the MobileKit Swift package, keyboard, native widgets and hosted tests. These sources belong to the Expo app and stay outside generated native projects.
- `apps/macos-platform/` — embedded Swift library for macOS system integrations; no product UI or second Rust engine.

The legacy SwiftUI iOS and macOS shells were retired by the user-approved [cleanup #75](https://github.com/pennel-app/pennel/issues/75). Their removal does not establish device, signed-upgrade, keyboard, Cloud or store acceptance; those gates remain open. Git history retains the original shells and visual reference.

**Desktop decision (2026-10-25): Pennel goes all-in on Tauri.** The shared desktop application is the only desktop product UI; Swift remains for Apple system integrations. **Mobile decision (2026-10-27): use Expo with generated native projects.** Swift/Kotlin own platform services and extensions, Rust owns product logic, and Expo owns the mobile application UI. See [mobile implementation and acceptance](docs/mobile.md).

## Roadmap tracking (mandatory)

Before implementing user-authorized features, fixes, or substantial documentation/configuration changes, read and follow the [agent workflow](docs/desktop-roadmap.md#agent-workflow). It governs issue reuse or creation, status updates, verification and handoff on the [Pennel roadmap](https://github.com/orgs/pennel-app/projects/1). If tracking access fails, continue authorized repository work and report the pending updates as the protocol describes.

## UI parity and look (mandatory)

The shared desktop application must look and behave **near-identically** on macOS, Windows and Linux, following the user-approved [Glaze design #92](https://github.com/pennel-app/pennel/issues/92): real system window chrome (no in-content title bar), locally bundled Inter, compact titles, neutral light/dark surfaces, inset rounded navigation and content panes, fine edges and consistent capsule controls. Keep Pennel's existing marks and real app icons where apps are listed. The original Swift app at commit `91775c1` remains a historical behavior reference; the approved Glaze design owns the desktop appearance.

- Same windows, tabs, sections, order, labels and empty/error states on every platform. Platform differences are limited to what the OS forces (window chrome, hotkey names: `fn` on Mac, Right Ctrl on Windows/Linux, system permission prompts).
- Same desktop visual system: palette, Inter typography, spacing, radii, component shapes and icons. Values come from the brand guide `assets/brand/brand.md` and canonical desktop theme tokens. Mobile retains its warm Figtree/Instrument Serif identity; artwork and the fixed dictation pill retain their existing brand colors. Do not change mobile branding through desktop overrides.
- Keep one search field in the sidebar; Cmd/Ctrl+F reveals and focuses it when the sidebar is collapsed. Align the header context with the reading column and keep New recording/Return to recording vertically centered and aligned with the content actions below.
- Same copy: the shared UI supports English and Dutch, defaults to the system’s first supported language (English fallback), and uses identical copy for the selected interface language on every platform. Interface language stays independent of speech recognition and user content.
- When a feature exists in the core, the shared app exposes it on every platform. If one platform cannot support it yet (e.g. echo cancellation, Apple dictation), show the same control disabled with a short reason rather than hiding it silently, and record the gap in `docs/desktop.md`.
- Review the look with screenshots of the app's own windows or headless renders, never by capturing the user's screen.
- Every PR that changes visuals must show before and after images (light and dark where the change affects both) in the PR description. Publish them on the `pr-assets` branch under `pr-<number>/` and embed them with `https://github.com/pennel-app/pennel/blob/pr-assets/pr-<number>/<name>.png?raw=true`, so images never enter the code history. Render both from the same input; mark mock renders as such.

## Build and test everything

Before calling any change done, build and test everything it can affect:

```sh
make core && make test                               # Rust core
(cd apps/desktop && npm ci && npm run build)          # desktop frontend
(cd apps/desktop/src-tauri && cargo test)             # desktop backend
(cd core && cargo fmt -- --check && cargo clippy --lib --tests -- -D warnings)
swift test --package-path apps/macos-platform          # affected Mac services
```

**macOS-first phase (2026-11-08, [#174](https://github.com/pennel-app/pennel/issues/174)).** Routine PR/main validation retains Mac core/native-platform checks, full Mac desktop frontend/backend/build/package checks and current iPhone/mobile checks. Routine Windows/Linux product tests, builds, installers and automatic releases are paused; shared platform source and UI parity rules remain. Lightweight Linux selector, packaging-helper and release/status jobs remain utility jobs. Selected CI jobs must stay green.

Manual `desktop.yml` and `decision-evaluation.yml` dispatches default to `platforms=macos`; `platforms=all` explicitly restores full-platform validation for that run. Signed desktop candidates also default to Mac and accept `all`, with their existing required version/build inputs. Manual validation never publishes releases. Resuming routine Windows/Linux validation or publication requires a deliberate policy/workflow change backed by current full-platform evidence; one manual run does not resume it. See [CI scope](docs/ci-performance.md#current-macos-first-phase-8-november-2026) and [releasing](docs/releasing.md).

Mobile changes also require the mobile workspace's type, unit, generation and native build checks. Keep core artifacts outside generated native projects, verify clean and repeated non-clean Prebuild, and preserve preview/production data and credential isolation. A simulator or build does not establish signed-device, keyboard cold-start, Cloud deployment or App Review acceptance. Keep Android implementation gated on the agreed iPhone acceptance. Record exact commands and outstanding gates in `docs/mobile.md`.

## Product rules

- Private by default: no telemetry, no account required, API keys only in the OS credential store, meetings are local Markdown files.
- Never log or transmit dictated text or meeting content except to the provider the user chose; logs hold timings, lengths and errors only.
- Untrusted text (transcripts, selections) must never be able to trigger actions: CLI agents run without tools in an empty folder; prompts wrap user text as data.
- Keep it light: no Electron, no heavy dependencies without a clear reason. Retain native Swift services behind the shared Tauri interface rather than rewriting working Apple integrations.
- Only claim what ships (README, website, release notes).

## Conventions

- Follow the public [contributor guide](CONTRIBUTING.md) for this repository’s coding and commit requirements.
- Tests first for logic (Rust unit tests in `core/`, Rust/TS tests in `apps/desktop`).

## Agent guidance

This repository uses GitHub Issues in `pennel-app/pennel`. Its public [roadmap agent workflow](docs/desktop-roadmap.md#agent-workflow), [contributor guide](CONTRIBUTING.md), product rules and build requirements remain usable without access to private maintainer records. Before exploration, read root `GLOSSARY.md` and relevant `docs/adr/` entries when present.

The Pennel team's shared maintainer guides live in private `pennel-app/pennel-home`. Resolve an explicit `PENNEL_HOME` first; otherwise walk the real ancestors of this checkout for the Home root when using nested worktrees, then try the canonical sibling `pennel-home` checkout. Verify Home's `AGENTS.md` and repository identity. From the resolved Home, read:

- `docs/agents/issue-tracker.md` before meaningful implementation or documentation work; always target this repository explicitly.
- `docs/agents/triage-labels.md` when triaging an issue.
- `docs/agents/domain.md` for glossary/ADR conventions; its paths resolve in this repository.
- `docs/agents/hoppscotch.md` for API-workspace metadata maintenance and the owning API repository's setup.

### Team knowledge (mandatory)

Before authorized Pennel execution work, read Home's `docs/agents/knowledge.md`, `docs/knowledge/README.md` and relevant topics. Before completion, follow that workflow to capture useful, verified reusable findings and automatically commit and push factual notes only. Instruction, skill or policy changes follow PR review. Read-only tasks and Plan mode defer writes; unrelated use of shared helpers does not trigger Pennel capture. If Home access or publishing is unavailable, retain notes locally and report capture or publication pending; keep private findings out of public records.

The shared files are also available in the private [Home repository](https://github.com/pennel-app/pennel-home/tree/main/docs/agents). Public contributors without Home access follow the local public requirements above; private Home access is not a build prerequisite.
